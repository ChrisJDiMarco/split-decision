# Fact-check verdicts

- **confirmed** (engines) DeepMind ships official MuJoCo WebAssembly bindings on npm as @mujoco/mujoco, versioned in lockstep with MuJoCo (3.14.0 published 2026-09-22), with a single-threaded build and a multi-threaded /mt build that needs COOP/COEP headers. The README still calls them WIP, with mjSpec untested in web apps.
  - Source: https://github.com/google-deepmind/mujoco/blob/main/wasm/README.md
- **confirmed** (engines) MuJoCo guarantees exact reproducibility only within a single version on the same architecture; shipping one pinned WASM binary everywhere is the route to cross-machine determinism, but that is an inference that must be tested.
  - Source: https://mujoco.readthedocs.io/en/stable/computation/index.html#reproducibility
- **partly-true** (engines) MuJoCo Warp claims near-feature-parity with MuJoCo (exceptions: PGS/noslip solvers, plugins, some flex features), runs in float32 on NVIDIA GPUs, and is the default backend in MuJoCo Playground; the same MJCF can therefore be trained on GPU and run in the browser.
  - Correction: The listed exceptions are incomplete. MJWarp also lacks the IMPLICITFAST midpoint integrator and, from its source, MuJoCo's new 'discrete' integrator (3.13) and 'pid' actuator (3.12). put_model raises NotImplementedError for them. So the same MJCF runs in both places only if it stays inside MJWarp's supported subset. Even then, training dynamics are float32 while browser MuJoCo WASM is float64, so the two are close but not identical sims. Also note that GPU training is the NVIDIA route the user has said he does not want.
  - Source: https://github.com/google-deepmind/mujoco_warp
- **confirmed** (engines) An existing public demo runs mjlab-trained Unitree G1 whole-body policies in the browser on @mujoco/mujoco plus onnxruntime-web at a 50 Hz policy rate, proving the train-on-GPU, run-in-browser pipeline.
  - Source: https://github.com/wbc-mjlab/wbc-demo
- **confirmed** (engines) MuJoCo 3.5–3.13 added actuator/sensor delays, a dcmotor actuator (inductance, cogging, thermal resistance variation, LuGre friction), gear-reflected actuator armature, a pid actuator with slew limits, and a discrete integrator that keeps stiff position servos stable at large timesteps.
  - Source: https://mujoco.readthedocs.io/en/latest/changelog.html
- **partly-true** (engines) MuJoCo has no continuous collision detection for rigid bodies (only CCD is flex-only ipc mode in 3.14), topology fixed at compile time, free joints only on children of the world body; fast weapons need analytic hit models and detachable parts must be top-level bodies bound by weld equalities toggled through eq_active.
  - Correction: 'Topology fixed at compile time' and 'must' are too strong. mjSpec plus mj_recompile can add or remove bodies and DOFs mid-simulation while keeping state. That is the alternative way to detach parts, though the WASM README says mjSpec is untested in web apps and recompiling is expensive per event. Weld plus eq_active is the practical pattern, but welds are soft constraints (solref/solimp), so attached parts show some compliance. The no-rigid-CCD point and the analytic-hit-model conclusion stand.
  - Source: https://mujoco.readthedocs.io/en/stable/XMLreference.html#body-joint-type
- **confirmed** (engines) In Rapier's TypeScript bindings on master (npm 0.21.0), the motor methods for revolute/prismatic multibody joints are commented out; from JS motorized robot joints are maximal-coordinate impulse joints, even though the Rust core has multibody armature and an MJCF loader.
  - Source: https://github.com/dimforge/rapier/blob/master/bindings/typescript/src.ts/dynamics/multibody_joint.ts
- **confirmed** (engines) PhysX reduced-coordinate articulation joints (basis of Unity's ArticulationBody) are not breakable, and Unity articulations have a maximum hierarchy depth of 64.
  - Source: https://docs.unity3d.com/6000.4/Documentation/Manual/physics-articulations.html
- **confirmed** (actuators) MuJoCo 3.7.0 (April 14, 2026) added a native dcmotor actuator with optional inductance, cogging, temperature-dependent resistance and LuGre friction; the latest release is 3.14.0 (Sep 22, 2026).
  - Source: https://mujoco.readthedocs.io/en/latest/changelog.html
- **confirmed** (actuators) The dcmotor model implements back-EMF torque-speed, current saturation, lumped I²R thermal ODE with R(T), reflected inertia J_r·N², and an onboard PID with voltage clamp (Vmax in gainprm[7], runtime-mutable); iron losses, magnet-flux derating and thermal current derating are explicitly NOT modeled.

  - Correction: ArticulationDrive does not expose 'only' stiffness/damping/forceLimit.
